# Human approval policy

The owner authorizes implementation and actions that expand approved scope. Faculty mentor and independent reviewer are planned review roles. Their eventual reviews provide scientific and reproduction evidence. They do not inherit owner authority.

| Gate | Approval evidence | Work enabled |
| --- | --- | --- |
| Implementation-first milestones | Completed design audit, agreed local CPU-only starting scope and written owner decision | Develop and verify approved components in dependency order. Build learning materials alongside verified implementation. |
| Open optional worker path | Reviewed task and its rights, tested runtime isolation and resource enforcement, registered executable identity and version, owner approval | Run that task pack within approved cap and policy |
| Start pilot or main study | Protocol and evaluator check, literature review, data permissions, pilot and sample justification where applicable, frozen hashes, reviewer dispositions | Approved study configuration and runs |
| Add new domain, expand policy or introduce model provider | Defined capabilities, task/data scope, budget, threat review, regression evidence, owner decision | The specifically scoped change |
| Transfer data, enable remote execution or spend | Named provider, approved datasets and location, access, deletion/retention, cap and expected usage, explicit owner approval | Only the authorized transfer, execution or spend |
| Publish code, artifacts, paper or results | License/rights, security, redaction and evidence review plus explicit owner approval | Only the named release or submission |

For a campaign record the approved protocol and policy digests, task profile, data scope, budget, approver identity and decision time. Reject pending, mismatched or revoked approval. Revoke by suspension and audited event. Record the review and approval reference in the project context or status. [Permission model](../security/PERMISSION_MODEL.md)
